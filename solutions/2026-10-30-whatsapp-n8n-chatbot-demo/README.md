# WhatsApp + n8n Chatbot Demo — Demo Proof #1 of 3

**Status: SIMULATION ONLY. No real WhatsApp message was sent. No live API
was called. No credential, phone number, or API key is used or stored
anywhere in this folder.**

A portfolio demo for Nitesh Kumar showing the shape of a WhatsApp chatbot
built on n8n: a WhatsApp-style webhook payload arrives, n8n parses and
routes it by intent (price / hours / human), a reply is composed, and a
send step fires. Every live part is replaced here by a clearly-labelled
mock, so the demo can be inspected and run without any Meta, WhatsApp, or
OpenAI account.

Fictional business used throughout: **Demo Traders**. Fictional customers
with placeholder IDs (`demo-customer-001`, …). Nothing here is a delivered
client bot, a production deployment, or a named client. No years of
experience are claimed.

## What this demo proves

- The webhook → parse → classify → route → compose → send flow works
  end to end on sample data, with the same reply logic in both the n8n
  workflow (`workflow.json`) and the local simulator (`simulator.py`).
- Intent routing works for the three intents in the brief: **price**,
  **hours**, and **human** (including the fallback: anything the keyword
  rules do not understand is routed to a human-handoff message).
- Malformed payloads are rejected safely instead of crashing the flow
  (the workflow returns a 400 response; the simulator returns an error
  object).
- The send step retries (up to 3 tries in the workflow) and points at a
  mock endpoint that can never resolve, so the demo cannot accidentally
  message anyone.

## Run the simulator

```sh
cd ~/workspace/demo-proofs/whatsapp-n8n-chatbot
python3 simulator.py                  # all 5 sample payloads
python3 simulator.py payloads/01-price.json   # one payload
python3 test_simulator.py -v          # run the tests
```

Requires Python 3 only. No third-party packages, no network access, no
credentials. Expected output: 5/5 payloads produce a reply; the unknown
question (`05-unknown.json`, "Do you sell purple elephants?") falls back
to the human-handoff message.

## Import the workflow into n8n

1. In n8n, choose **Import from File** and select `workflow.json`.
2. Inspect the nodes. The workflow is **inactive** on import
   (`"active": false`).
3. The **Send via Mock Endpoint** node posts to
   `https://mock-endpoint.invalid/demo-whatsapp/send`. The `.invalid`
   domain can never resolve — this is deliberate. Do not point it at a
   real endpoint without completing the live-deployment steps below.
4. The **OpenAI Reply (DISABLED - live variant only)** node is disabled
   and connected to nothing. It shows where a live model call would sit
   and names the environment variable it would need
   (`OPENAI_API_KEY`). No key is in this file, and no key should ever be
   pasted into a workflow file — supply it through n8n credentials.

**n8n was not run on this machine** (n8n is not installed here), so the
workflow has **not** been import-tested in n8n. What was verified
instead: `workflow.json` parses as valid JSON, contains the required
nodes and connections, and the simulator implementing the same logic
passes all tests. See `VERIFY.txt`.

## Simulated vs live — exactly what is still needed

| Part | In this demo | Live deployment still needs |
|---|---|---|
| Inbound message | Sample JSON files in `payloads/` | A Meta developer app, a WhatsApp Business number, and webhook verification completed in Meta |
| Reply logic | Keyword rules + fixed templates (MOCK responder) | Either keep rules, or enable the OpenAI node with a key supplied through n8n credentials |
| Send step | Mock `.invalid` endpoint; no request is made | The WhatsApp Cloud API send endpoint, with the business number ID and access token supplied through n8n credentials (environment variable names only are recorded in the workflow notes; no values are stored here) |
| Human handoff | Template text only; no human is contacted | A real handoff route (inbox, on-call person, or CRM) agreed with the client |
| Verification | None — samples are trusted local files | Webhook signature verification against the verify token, implemented before the workflow goes live |

Environment variable **names** a live deployment would need (no values
stored anywhere in this demo): `WHATSAPP_VERIFY_TOKEN`,
`WHATSAPP_BUSINESS_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, `OPENAI_API_KEY`.
All are supplied by the client or by Nitesh at deployment time, through
n8n credentials — never in chat, files, or screenshots.

## Limitations

- **No real WhatsApp message was sent, and no live API was called** — not
  by the simulator, not by the workflow, not by any test.
- The mock responder is keyword rules, not a language model. It cannot
  handle questions outside its three intents except by falling back to
  the human-handoff message. That fallback is a feature of the demo, not
  evidence of general conversational ability.
- The workflow JSON has not been import-tested in n8n (n8n is not
  installed on this machine). Node types and settings follow n8n's
  export format as documented, but a live import may need small
  adjustments for the n8n version in use.
- The demo prices, hours, and business details are invented for
  "Demo Traders" and must be replaced with the real client's details
  before any live use.
- An earlier WhatsApp webhook template (handshake + HMAC checks, built
  6 October 2026) was used as pattern reference only. Signature
  verification is **not** implemented in this demo and must be added
  before a live deployment.
- This demo proves the flow and the reply logic only. It is not a
  delivered client project, and it must not be described as one.
